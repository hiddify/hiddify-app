# Исследование: выбор Open Source VPN-клиента для форка, ребрендинга и публикации

**Дата исследования:** 13 июля 2026
**Метод:** живой поиск и проверка GitHub-репозиториев (звёзды, лицензии, даты коммитов проверены на дату исследования через WebSearch/GitHub fetch). Там, где данные не удалось верифицировать напрямую — это явно помечено.

---

## TL;DR (если читать только это)

Для твоего кейса (iOS-приоритет, обучение, форк + ребренд + свои сервера, максимальное переиспользование кода между платформами, текущий бэкенд Xray/VLESS) три реалистичных кандидата:

1. **Hiddify (hiddify-app)** — самый широкий охват платформ и протоколов, один код на Flutter+Go/sing-box.
2. **Karing** — самый активно обновляемый, тоже Flutter+sing-box, есть прецедент публикации в App Store под своим именем.
3. **OneXray (бывший FoXray)** — компактный, честный Xray-core-клиент, GPL-3.0 без доп. условий, тоже уже опубликован в App Store и Google Play под своим именем.

Все три построены вокруг **sing-box** или **Xray-core**, поддерживают VLESS/Reality, и минимум два из трёх (Hiddify, Karing) также поддерживают Hysteria2 — то есть тебе не придётся выбирать между "остаться на Xray/VLESS" и "добавить Hysteria2/sing-box": в этих клиентах это уже есть одновременно, переключение — вопрос конфига, а не архитектуры.

Ниже — полное исследование по всем 9 пунктам твоего запроса.

## Часть 3. Что внутри — архитектура

| Проект | Язык UI | Ядро | Модель конфигурации |
|---|---|---|---|
| Hiddify | Dart/Flutter (72%) + Kotlin/Swift-шимы | Go, модуль `hiddify-core` поверх **sing-box** | Подписки: sing-box/V2Ray/Clash/Clash Meta JSON/YAML |
| Karing | Dart/Flutter (98%) + тонкие нативные шимы | форк **sing-box** (`KaringX/sing-box`) | Подписки: Clash YAML + sing-box JSON |
| OneXray | Dart/Flutter (79%) + Swift/Kotlin | **Xray-core** через `libXray` | VLESS/VMess/Trojan/SS-ссылки, XHTTP/gRPC/WS транспорты |
| SFI/SFM (SagerNet) | Swift (92%) + C | нативный **libbox** (sing-box) | sing-box JSON, "эталонная" реализация |
| v2rayNG / v2rayN | Kotlin / C# | Xray-core (+ sing-box опционально в v2rayN) | ссылки-конфиги, подписки |
| Clash Verge Rev | Rust + TypeScript (Tauri 2) | mihomo (Clash.Meta) | Clash YAML, поддержка тем/CSS |
| FlClash | Dart/Flutter + Kotlin/C++/Go/Rust | mihomo | Clash YAML |
| AmneziaVPN | C++/QML (Qt) | набор демонов в Docker-контейнерах на **твоём** сервере | собственный протокол разворачивания через SSH |

**Плюсы/минусы подходов:**

- **Flutter + Go-ядро (Hiddify, Karing, OneXray)** — максимум переиспользования кода между iOS/Android/Windows/macOS/Linux (один UI-код, ядро компилируется как нативная библиотека через gomobile/cgo). Минус: Flutter на iOS даёт не самый "нативный" UX, приложение тяжелее по размеру, отладка сетевого расширения (Network Extension) на iOS всё равно требует Swift-обвязки.
- **Нативный Swift (SFI/SFM)** — лучший UX и производительность на Apple-платформах, но нулевое переиспользование кода на Android/Windows — там нужен отдельный SFA (Kotlin) и т.д. Три разных кодовых базы, синхронизировать логику вручную.
- **Rust/Tauri (Clash Verge Rev)** — отличный десктоп-опыт, компактные бинарники, но **не имеет пути на iOS** в принципе (Tauri — десктопный/веб-фреймворк, мобильная поддержка экспериментальна и не покрывает iOS Network Extension модель).
- **C#/.NET (v2rayN)** — только Windows-экосистема, для iOS неприменимо.
- **Собственное ядро в Docker на сервере (Amnezia)** — гибко для сервера, но клиентская часть архитектурно "толще" и не подписочная, а SSH-деплой-ориентированная — не то, что тебе нужно, раз у тебя уже есть свои Xray/VLESS-сервера с готовыми ссылками-подписками.

## Часть 5. Три лучших варианта именно для тебя

### 🥇 Вариант 1 — Hiddify (hiddify-app)

**Почему:** единственный из тройки с по-настоящему полным покрытием всех пяти твоих платформ (iOS, Android, Windows, Linux, macOS) из одной кодовой базы, самый широкий протокольный набор (VLESS+Reality+Hysteria2+TUIC+WireGuard одновременно), огромное сообщество (~31k звёзд) — значит, много документации, issues, готовых ответов на твои будущие вопросы.

**Проблемы/ограничения:**
- Лицензия — GPLv3 **"с дополнительными условиями"** (LICENSE.md), которые касаются публикации через GitHub Actions, атрибуции автора и, возможно, ограничений на ре-паблишинг под своим именем в сторах — **это нужно прочитать целиком до старта**, я не могу дать здесь 100% юридическую гарантию.
- Крупная кодовая база (Flutter + Go + нативные шимы) — для новичка порог входа выше, чем у OneXray.
- Темп релизов на дату исследования выглядит слегка замедлившимся (~4 месяца без релиза) — стоит проверить активность репозитория на момент старта твоей работы.

**Время на освоение:** для человека, уже настроившего Xray/VLESS-сервер, но не писавшего мобильные приложения — реалистично 3–6 недель до первой рабочей пересобранной версии под iOS (включая разбор Flutter, gomobile-сборки ядра, Network Extension в Xcode).

**Перспективность:** высокая — крупнейший активный игрок в этой нише с реальным продакшн-использованием.

---

### 🥈 Вариант 2 — Karing

**Почему:** самый активно обновляемый проект в списке (релиз буквально за неделю до даты исследования), тоже Flutter+sing-box (значит, тот же принцип максимального переиспользования кода между платформами), при этом заметно компактнее Hiddify — легче разобраться. Есть живой прецедент публикации в Apple App Store и на tvOS под собственным именем — то есть путь "форк → ребренд → публикация" уже кем-то пройден на этой кодовой базе (косвенно, но обнадёживающе).

**Проблемы/ограничения:**
- Нет нативной поддержки Hysteria (v1), только Hysteria2 — если тебе принципиально важен именно Hysteria1, это не сюда.
- Встроенная синхронизация через iCloud/WebDAV — если будешь ребрендить, придётся решить, что делать с этой инфраструктурой (отключить или подменить на свою).
- Меньше публичной документации по внутреннему устройству, чем у Hiddify — придётся больше читать сам код.

**Время на освоение:** 2–5 недель, за счёт более компактной базы может быть даже быстрее, чем Hiddify.

**Перспективность:** хорошая — растущий проект с частыми релизами, но сообщество на порядок меньше, чем у Hiddify (меньше готовых ответов на форумах).

---

### 🥉 Вариант 3 — OneXray (бывший FoXray)

**Почему:** самый маленький и самый "честный" вариант — чистый Xray-core-клиент без лишней сложности (без параллельного sing-box-ядра, без Clash-совместимости). Если твоя цель — именно **понять архитектуру** и не утонуть в코де, это лучший учебный вариант. Уже опубликован и в App Store, и в Google Play под собственным именем — прямое доказательство, что Apple такие приложения пропускает. Чистая лицензия GPL-3.0 без дополнительных условий.

**Проблемы/ограничения:**
- Нет Hysteria2/TUIC/sing-box/WireGuard — если решишь мигрировать с чистого VLESS на что-то из этого списка, придётся добавлять ядро sing-box самостоятельно (существенная работа).
- Маленькое сообщество (~270 звёзд) — меньше готовых решений на форумах, придётся больше самому разбираться и, возможно, писать в issues автору напрямую.
- Меньше платформ "из коробки" по сравнению с Hiddify/Karing нужно перепроверить фактическую готовность Windows/Linux-сборок на момент старта.

**Время на освоение:** 1–3 недели — самый быстрый путь к первому рабочему форку именно потому, что кода меньше.

**Перспективность:** ограниченная как у самостоятельного продукта (маленькая команда), но как **учебная база для форка** — отличная, поскольку архитектурно прозрачнее всего.

---

### Почему не остальные

- **SFI/SFM (официальные клиенты sing-box от SagerNet)** — эталонная реализация, но лицензия прямо запрещает ребрендинг/использование имени без согласия автора — юридически самый рискованный вариант именно для твоей цели (ребренд+публикация).
- **v2rayNG / v2rayN / Clash Verge Rev / FlClash** — отличные проекты, но у каждого по отдельности нет iOS, а у тебя iOS — платформа №1. Их можно рассмотреть **как источник для Android/Windows/Linux-версий**, если решишь не тащить один код на все платформы, а собирать разные клиенты под разные ОС (см. Часть 6, Вариант B).
- **AmneziaVPN** — сильный проект, но архитектурно "сервер разворачивается через SSH", а не "подписка вставляется в клиент" — не твоя модель.
- **Passepartout/Outline** — не поддерживают VLESS в принципе, не подходят по протоколу.

## Часть 6. Варианты архитектуры твоего приложения

### Вариант A — Моно-клиент на Flutter+sing-box (форк Hiddify или Karing)

```
        ┌─────────────────────────────┐
        │      Flutter UI (Dart)      │   ← один код для iOS/Android/Win/macOS/Linux
        └──────────────┬──────────────┘
                        │ platform channel / FFI
        ┌──────────────▼──────────────┐
        │   sing-box core (Go, libbox) │   ← поддерживает VLESS, Reality,
        │                              │      Hysteria2, TUIC, WireGuard
        └──────────────┬──────────────┘
                        │
        ┌───────────────────────────────┐
        │   iOS: Network Extension       │
        │   Android: VpnService          │
        │   Desktop: TUN/системный стек  │
        └──────────────┬────────────────┘
                        │
                 ┌──────▼──────┐
                 │  твой сервер │  (VLESS/Reality/Hysteria2 — выбор в конфиге)
                 └─────────────┘
```

**Плюсы:** максимум переиспользования кода (ты этого и хотел), протокол выбирается конфигом, а не архитектурой — не нужно заранее решать "остаться на VLESS или перейти на Hysteria2", можно поддержать оба сразу.
**Минусы:** Flutter — дополнительный слой абстракции, iOS-сборка (Network Extension, entitlements, TestFlight) всё равно требует отдельного глубокого погружения в Xcode независимо от того, что UI на Dart.

### Вариант B — Отдельные нативные клиенты по платформам

```
iOS (Swift, форк SFI)        Android (Kotlin, форк v2rayNG/NekoBox)      Windows (C#, форк v2rayN)
        │                              │                                          │
        └──────────────┬───────────────┴──────────────────────┬───────────────────┘
                        │                                      │
                  VLESS/Reality                          VLESS/Hysteria2
                        │                                      │
                        └──────────────────┬───────────────────┘
                                     твой сервер
```

**Плюсы:** каждая платформа получает самый нативный, отполированный UX; можно опираться на самый зрелый проект под каждую ОС отдельно.
**Минусы:** ноль переиспользования кода, три-пять отдельных кодовых баз, тройная работа по багфиксам и обновлениям протоколов — прямо противоречит твоему требованию "максимально переиспользовать код между платформами". Не рекомендую как основной путь.

### Вариант C — Только Xray/VLESS (минимальный, текущий стек)

```
iOS/Android/Desktop клиент (форк OneXray)
        │
     Xray-core
        │
      VLESS (+ Reality опционально)
        │
   твой сервер
```

**Плюсы:** самый простой для понимания, у тебя уже есть рабочий сервер под это, минимум движущихся частей — лучший вариант, если цель именно **понять весь процесс от и до**, а не построить максимально "будущеустойчивый" продукт.
**Минусы:** если позже понадобится Hysteria2 (лучше проходит через некоторые типы DPI/блокировок за счёт QUIC/UDP) — придётся добавлять второе ядро (sing-box) отдельно, это не тривиальная доработка.

### Рекомендация по архитектуре

Для обучения — **начни с Варианта C** (форк OneXray, чистый Xray/VLESS, самая короткая дистанция до "я это понял и собрал сам"). Когда освоишься — **мигрируй на Вариант A** (форк Hiddify/Karing), который тебе даст и мультипротокольность, и кросс-платформенность без второго полного цикла обучения "с нуля", потому что понимание Xray-core, которое ты получишь на Варианте C, напрямую переносится на работу с sing-box (те же концепции: inbound/outbound, роутинг, DNS).

## Часть 7. Docker — нужен ли тебе и зачем вообще

### Зачем Docker используется в VPN-проектах в принципе

1. **Развёртывание сервера.** Панели управления Xray/VLESS-серверами (3x-ui, Marzban, Marzneshin и подобные) по умолчанию разворачиваются через `docker compose up` — это де-факто стандарт индустрии для self-hosted VPN-панелей, потому что изолирует Xray-core, базу данных и веб-панель друг от друга и от хостовой ОС.
2. **Воспроизводимая сборка бэкенд-компонентов.** Go-бинарники (Xray-core, sing-box) собираются в чистом Docker-окружении в CI, чтобы результат не зависел от того, какая версия Go установлена на машине разработчика.
3. **CI/CD.** GitHub Actions под капотом почти всегда гоняет джобы в контейнерах — сборка Android APK, Linux AppImage/deb/rpm, кросс-компиляция под разные архитектуры (arm64/amd64) удобно параллелится через Docker-образы.
4. **Тестовые серверы.** Поднять локальный VLESS/Hysteria2-сервер для отладки клиента за 2 команды — Docker для этого удобнее, чем ручная установка Xray на голую машину.

### Нужен ли Docker лично тебе

Да, но **точечно**, а не как основа всего процесса:

| Задача | Нужен ли Docker | Почему |
|---|:---:|---|
| Разработка iOS-клиента (Xcode, Swift, Network Extension) | ❌ Нет | Xcode физически требует macOS, Docker на Linux/Windows тут не поможет вообще — это не решаемо контейнеризацией |
| Сборка Flutter-приложения (Dart-часть) | ➖ Не обязателен | Flutter SDK ставится локально без Docker, но можно гонять сборку в контейнере ради чистоты CI |
| Компиляция sing-box/Xray-core ядра (Go) | ✅ Полезен | Быстро получить воспроизводимую сборку под нужную архитектуру без замусоривания локальной системы Go-тулчейнами разных версий |
| Развёртывание/апгрейд твоего VLESS-сервера | ✅ Да, стандарт индустрии | 3x-ui/Marzban и подобные панели "из коробки" рассчитаны на docker compose |
| Подписание приложения (сертификаты Apple, App Store Connect) | ❌ Нет | Требует реального Keychain/Xcode на macOS, не докеризуется |
| Локальное тестирование протокола (поднять тестовый сервер) | ✅ Удобно | `docker run` с готовым образом Xray/sing-box — секунды вместо ручной установки |
| CI/CD пайплайн (сборка Android/Windows/Linux версий) | ✅ Да | Индустриальный стандарт для GitHub Actions runners |

### Где Docker — стандарт индустрии, а где избыточен

- **Стандарт:** серверная сторона (панели управления, сам Xray/sing-box демон на VPS), CI для Android/Linux-сборок.
- **Избыточен/бесполезен:** весь iOS/macOS pipeline (сборка, подпись, публикация) — Apple жёстко привязывает это к своей экосистеме (Xcode, Keychain, notarization), никакой Docker это не обходит и не ускоряет. Также не нужен для чистой Flutter/Dart-разработки UI — там свой набор инструментов (`flutter build`), Docker добавит сложность без выгоды.

**Вывод:** заведи себе Docker для (а) быстрого локального тестового VLESS/Hysteria2-сервера и (б) деплоя своей боевой панели (3x-ui/Marzban) — это сэкономит реальное время. Не пытайся "докеризировать" iOS-часть — там Docker не решает ни одной твоей задачи.

        ↓

### Этап 2 — Выбор клиента
- **Изучить:** структуру репозитория, README, CONTRIBUTING.md, лицензию целиком (не только заголовок — читай LICENSE.md полностью, особенно у Hiddify/SagerNet, где есть доп. условия).
- **Инструменты:** git, GitHub аккаунт, базовое чтение Dart/Kotlin/Swift кода.
- **Риски:** выбрать проект, у которого сборка "из коробки" не работает без танцев с бубном (частая проблема у сложных мультиплатформенных репо). **Как избежать:** до форка попробуй собрать апстрим-версию как есть, следуя официальному README, прежде чем что-либо менять.

### Этап 3 — Форк и первая сборка
- **Изучить:** Xcode-проект (для iOS-части), gomobile/cgo (если ядро на Go нужно пересобирать), систему сборки Flutter (`flutter build ios`).
- **Инструменты:** Xcode последней версии, macOS-машина (для iOS-сборки обязательна — виртуалка/облако тоже подойдёт, если нет своего Mac), CocoaPods/Swift Package Manager, Flutter SDK, Android Studio (если параллельно собираешь Android).
- **Риски:** несовпадение версий Xcode/Flutter/Go с теми, что использовал автор апстрима → ошибки сборки. **Как избежать:** зафиксировать версии через `.tool-versions`/README апстрима, использовать именно указанные там версии, а не последние доступные.

### Этап 4 — Ребрендинг
- **Изучить:** структуру Assets.xcassets (иконки iOS), `pubspec.yaml`/`Info.plist` (имя приложения, bundle identifier), локализационные файлы, цветовые темы (обычно в отдельном theme/config файле у Flutter-проектов).
- **Инструменты:** Figma/любой графический редактор для иконки (Apple требует набор размеров — используй генератор App Icon), find-and-replace по кодовой базе для смены bundle id (важно поменять **везде**, включая entitlements и Network Extension target).
- **Риски:** забытые упоминания оригинального имени/bundle id в конфигах Network Extension → приложение либо не соберётся, либо конфликтует с оригинальным при установке на одно устройство. **Как избежать:** grep по всему репозиторию на оригинальное имя пакета/bundle id перед сборкой релиза.

### Этап 5 — Подключение своих серверов
- **Изучить:** формат конфигов клиента (VLESS-ссылки `vless://...`, JSON sing-box, YAML Clash — зависит от выбранного клиента), механизм подписок (URL, откуда клиент тянет список серверов).
- **Инструменты:** твоя существующая Xray/VLESS-инфраструктура, панель управления (3x-ui/Marzban, если используешь), генератор подписочных ссылок.
- **Риски:** формат конфига форкнутого клиента может не совпадать 1:1 с тем, что генерирует твоя текущая панель (например, если панель заточена под чистый Xray, а клиент ждёт sing-box JSON). **Как избежать:** явно проверить формат на тестовом сервере до релиза, при необходимости написать небольшой конвертер конфигов.

### Этап 6 — Сборка (Release)
- **Изучить:** отличия Debug/Release сборки (оптимизация, отключение логов, ProGuard/R8 для Android, обфускация Dart для Flutter).
- **Инструменты:** fastlane (сильно упрощает iOS/Android релизные сборки и загрузку в сторы), CI (GitHub Actions с готовыми workflow, часто уже есть в апстрим-репозитории — их можно адаптировать под свой bundle id/секреты).
- **Риски:** утечка отладочных логов/API-ключей апстрима в релизную сборку. **Как избежать:** явно пройтись по всем `.env`/секретным файлам апстрима и заменить на свои перед первой публичной сборкой.

### Этап 7 — Подписание
- **Изучить:** Apple Developer Program (обязательна платная подписка, $99/год), процесс создания App ID, Provisioning Profiles, entitlements для Network Extension (Apple требует **отдельное разрешение** — "Network Extension entitlement" — для VPN-функциональности, оно не выдаётся автоматически всем аккаунтам сразу).
- **Инструменты:** Xcode, Apple Developer аккаунт, (опционально) fastlane match для управления сертификатами в команде.
- **Риски:** заявка на Network Extension entitlement может потребовать времени на одобрение Apple, а без него VPN-функциональность в App Store-сборке физически не заработает. **Как избежать:** подать заявку на entitlement максимально рано, ещё на этапе 2-3, не откладывая на предпубликационный этап.

### Этап 8 — Тестирование
- **Изучить:** TestFlight (iOS beta-тестирование), внутреннее тестирование Google Play, ручное тестирование реального подключения через разные протоколы/сети (Wi-Fi, мобильный интернет, разные страны при возможности).
- **Инструменты:** TestFlight, Firebase App Distribution (для Android, опционально), реальные устройства (эмуляторы не всегда корректно эмулируют VPN/Network Extension поведение).
- **Риски:** приложение работает в разработке (Xcode-запуск), но падает в TestFlight-сборке из-за отличий в entitlements/подписи. **Как избежать:** тестировать именно TestFlight-сборку, а не только локальный запуск через Xcode, до подачи на ревью.

### Этап 9 — Публикация
- **Изучить:** App Store Review Guidelines, раздел про VPN-приложения (Apple исторически внимательно проверяет VPN-функциональность, политику логирования, наличие политики конфиденциальности), Google Play Developer Policy для VPN-категории (аналогично, требует декларации в Data Safety форме).
- **Инструменты:** App Store Connect, Google Play Console, готовая Privacy Policy (обязательна для VPN-приложений на обеих платформах — можно сгенерировать шаблон и адаптировать под реальную практику логирования твоего сервиса).
- **Риски:** отклонение на ревью из-за отсутствия/неполноты Privacy Policy, неясного объяснения зачем нужен полный туннель трафика, или сходства с оригинальным заброшенным/забаненным приложением (Apple иногда сверяет "клоны"). **Как избежать:** написать честное, подробное описание функциональности и политику приватности до подачи, максимально дистанцировать визуально/текстово от апстрим-бренда (ты и так это планируешь).

### Этап 10 — Поддержка
- **Изучить:** git rebase/merge стратегию для регулярного подтягивания обновлений апстрима (особенно важно для security-патчей в Xray-core/sing-box — там регулярно фиксят уязвимости и улучшают обход блокировок), мониторинг падений (Crashlytics/Sentry).
- **Инструменты:** git (upstream remote + периодический rebase твоих ребренд-патчей на новые версии апстрима), система крэш-репортов.
- **Риски:** твой форк со временем "расходится" с апстримом настолько, что подтягивать обновления становится больно (particularly если ты сильно переписал UI). **Как избежать:** держать ребрендинг/кастомизацию максимально изолированной (отдельные файлы иконок/тем/конфигов, минимум правок в "ядровых" файлах апстрима) — это стандартная практика для форков, которые планируют долгосрочно following upstream.

## Часть 9. Итоговая практическая рекомендация

> Если бы я начинал такой проект сегодня с нуля, имея целью обучение и получение собственного VPN-клиента, я бы построил его в два прохода:
>
> **Проход 1 (обучение, 2–4 недели): форкнуть OneXray.** Это самый компактный, "прозрачный" Xray-core-клиент на Flutter — там достаточно кода, чтобы понять всю архитектуру (inbound/outbound, VLESS/Reality, как ядро прокидывается в Network Extension на iOS), но недостаточно, чтобы утонуть. Плюс это уже кем-то опубликовано в App Store — прямое доказательство, что путь рабочий. Пройти на нём весь цикл: форк → ребренд → свой сервер → сборка → подпись → TestFlight → публикация.
>
> **Проход 2 (продакшн-версия, ещё 3–6 недель): мигрировать на форк Hiddify или Karing.** Concepts, полученные на Xray-core, напрямую переносятся на sing-box (тот же mental model). Это даст тебе VLESS+Reality+Hysteria2+TUIC одновременно, без необходимости выбирать протокол на архитектурном уровне — только конфигом, и полное покрытие всех пяти твоих платформ из одной Flutter+Go кодовой базы, что прямо отвечает твоему требованию "максимально переиспользовать код между платформами". Между Hiddify и Karing выбирай по факту: если к моменту старта у Hiddify темп релизов восстановится и лицензия при внимательном чтении окажется некритичной — бери его (шире аудитория, больше документации). Если лицензия Hiddify покажется рискованной для твоих целей — Karing даёт почти то же самое с более чистой лицензией и более частыми релизами.
>
> Я бы **не** начинал сразу с официальных SFI/SFM от SagerNet (юридический риск ребрендинга) и **не** пытался с первого дня собрать "монолит на все протоколы сразу" — это распыляет внимание в фазе обучения, где ценнее один раз глубоко понять полный цикл на простом проекте.

## Что осталось непроверенным / требует уточнения на твоей стороне

- **Лицензия Hiddify "с дополнительными условиями"** — я описал факт её существования, но не разбирал построчно юридические детали. Прочитай `LICENSE.md` в репозитории полностью перед стартом, при сомнениях — можно проконсультироваться отдельно (я не заменяю юриста).
- **Репозиторий mihomo (MetaCubeX/mihomo)** — на дату исследования отдаёт не тот контент, что ожидается. Это касается тебя постольку, поскольку Clash Verge Rev/FlClash используют mihomo как ядро — их текущая работоспособность подтверждена (они используют закреплённые версии), но если решишь смотреть в сторону mihomo-based клиентов, сначала проверь состояние репозитория вручную.
- **Актуальное состояние Windows/Linux-сборок OneXray** — в исследовании подтверждено официальное упоминание этих платформ, но не проверялась фактическая работоспособность билдов на дату исследования — стоит скачать и проверить самому перед тем, как на них полагаться.
- **Точные текущие цифры звёзд/форков** — даны с пометкой "приблизительно", это снимок на дату исследования (13.07.2026), к моменту твоего старта они изменятся (в бо́льшую сторону, скорее всего, если проекты остаются активными) — не критично для решения, но не воспринимай числа как точные до единицы.
